01Why you are doing this

This is not a test of whether you can write code. It is a test of whether you can direct an AI to build something real, and then stand behind what it produced.

The industry has already moved. The junior developers getting hired now are the ones who can take a vague requirement, break it down, drive an AI through the build, and then defend the result in code review. The ones who paste prompts and hope are the ones being filtered out.

By the end of this you will have a production-shaped application you can show anyone, a public repository with real history and a working pipeline, and a clear picture of where your gaps are so we can close them deliberately.

The gaps are the point. Do not hide them.

02What you are building

Testify, a lightweight test run and defect tracker.

You know this domain already, which is deliberate. You should not be spending energy working out what the product does. Spend it on the engineering.

Core functionality

Projects

  • Create a project with a name and description.
  • List and view projects.

Test cases

  • Belong to a project.
  • Title, preconditions, steps, expected result, priority (Low, Medium, High, Critical).
  • Full create, read, update, delete.

Test runs

  • Created against a project, pulling in a selected set of test cases.
  • Each case in a run carries a result: Not run Pass Fail Blocked
  • A run is In progress or Complete, and shows a live pass rate.

Defects

  • Raised from a failed test case inside a run.
  • Title, description, severity, status (Open, In progress, Resolved, Closed).
  • Links back to the test case and run that produced it.

Dashboard

  • Per project: total cases, runs completed, current pass rate, open defects by severity.

Out of scope. No email notifications, file attachments, comment threads, real-time updates, mobile apps, or integration with a real test tool.

If you finish early, go to the stretch goals. Scope creep is a fail condition, not initiative.

03Technical requirements

Choose your API language from TypeScript (Node), C# and .NET, Go, or Ruby on Rails. Pick the one you want to be interviewed on. Everything else below is fixed.

Web application

  • React with TypeScript. No plain JavaScript.
  • Client-side routing covering: project list, project detail, test case editor, run execution, defect list, dashboard.
  • Loading, empty and error states on every view that fetches data. An empty table with no message is unfinished work.
  • Client-side validation that matches the server, not a looser version of it.
  • No secrets, keys or tokens in the frontend bundle.

API

  • RESTful, versioned under /api/v1.
  • Correct verbs and status codes. A failed create returns 4xx, not 200 with an error in the body.
  • One consistent error response shape across every endpoint.
  • Server-side validation on every write. Never trust the client.
  • Pagination anywhere a list can grow unbounded.
  • An OpenAPI spec, generated or hand-written, served by the app.
  • PostgreSQL, with the schema managed by migrations rather than by hand.

Containerization

  • A Dockerfile for the API and one for the web app.
  • Multi-stage builds. Your final images must not carry build tooling or source.
  • Containers run as a non-root user.
  • docker compose up from a clean clone gives a working environment: API, web, database, migrations applied.
  • A .dockerignore that excludes what it should.
  • Record your image sizes in the README, and be able to explain them.

Infrastructure

  • Infrastructure as code. Terraform preferred; Pulumi or a documented equivalent is fine.
  • Configuration through environment variables only. Nothing environment-specific baked into an image.
  • Local and deployed environments kept properly separate.
  • A health endpoint reporting application and database status, wired into your deployment platform.
  • A documented persistence or backup strategy, even if you do not automate it.

Security

This is not optional polish. Treat it as core.

  • Registration and login. Passwords hashed with bcrypt or argon2. Never plain text, never MD5 or SHA1.
  • Sessions via JWT or secure HTTP-only cookies, with your choice justified in writing.
  • A user can only see and modify data in projects they belong to. Prove it with a test.
  • Input validation and output encoding on every user-supplied field.
  • Parameterised queries or an ORM. No string-concatenated SQL anywhere.
  • Rate limiting on the authentication endpoints.
  • Security headers set: CSP, HSTS, X-Content-Type-Options, X-Frame-Options.
  • CORS locked to a known origin, never *.
  • Secrets in GitHub Secrets and environment variables. If one lands in a commit, rotate it and write up what happened.
  • Dependency scanning on (Dependabot or Trivy), with findings triaged rather than ignored.
  • A SECURITY.md naming which OWASP Top 10 risks you addressed, how, and which ones you knowingly did not.

GitHub and deployment

  • Public repository with meaningful commit history. One giant "initial commit" is a fail.
  • Short-lived branches. Every change reaches main through a pull request, including your own.
  • A pull request template, and descriptions that explain the change.
  • Actions pipeline on every pull request: lint, type-check, test, build both images.
  • On merge to main: build, push, deploy.
  • Publicly reachable over HTTPS. Fly.io, Render, Railway or AWS free tier are all fine. Cheapest thing that works.
  • Branch protection on main requiring the pipeline to pass.
  • Pipeline status badge in the README.

Testing

You are a QA. This is your strength, so the bar here is higher than elsewhere.

  • Unit tests on business logic: pass rate calculation, status transitions, authorization rules.
  • Integration tests against the API, hitting a real database in a container.
  • At least six end-to-end tests (Playwright or Cypress): register, log in, create a project, create a case, execute a run, raise a defect.
  • Tests run in CI and block the merge when they fail.
  • A short written test strategy: what you test at each level, and why.

04How you must work with AI

Use AI aggressively. That is the whole point. These five rules are not negotiable.

  1. You own every line. If it is in your repository, you can explain it. "The AI wrote it" is not an answer in a code review, an interview, or an incident.
  2. Keep a decision log. Maintain docs/DECISIONS.md, one entry per significant decision rather than per prompt. I expect fifteen to thirty entries by the end.
  3. Verify every security and infrastructure suggestion. Models are confidently wrong about auth, CORS, container permissions and IAM more often than anywhere else. Check it against primary documentation and record the source.
  4. Prompt small. "Build me a test management app" produces something you cannot maintain. Work at the level of one endpoint, one component, one migration. If a response is longer than you can review carefully, the prompt was too big.
  5. Log where AI cost you time. Hallucinated APIs, outdated patterns, code that looked right and was not. This is not a criticism of the tooling. Knowing its failure modes is the skill.

Decision log format

## [Date] [Decision]

Context: what I was trying to do
What I asked: the substance of the prompt
What it gave me: summarised
What I changed and why: the important part
What I did not understand at first: be honest here

That last field is the most valuable thing in this exercise. Do not sanitise it.

The walkthrough

Forty-five minutes at the end. I will:

  1. Pick three files at random and ask you to walk me through them.
  2. Ask you to make a small change live, with no AI assistance.
  3. Ask you to explain one security decision and one infrastructure decision in depth.
  4. Ask what you would do differently with another two weeks.

A working application on its own does not pass this. A deployed app you cannot explain scores lower than a partly finished one you can.

08Stretch goals

Only once the definition of done is signed off.

  • Role-based access control (admin, tester, viewer) with tests proving each boundary.
  • Structured logging with correlation IDs traced from browser through to database.

  • Run history and a pass rate trend over time.
  • An ephemeral preview environment per pull request.

09Getting unstuck

Ask me anything, at any point, on one condition: tell me what you already tried and what the AI told you.

"This does not work" gets you a question back. "I asked for X, got Y, expected Z, and here is what I checked" gets you a real answer.

Being stuck is not the failure. Being stuck quietly for two days is.
